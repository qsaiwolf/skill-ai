# agy-error-protocol

بروتوكول منهجي لتصحيح الأخطاء — يمنع الفخ الأكثر شيوعاً: إعادة كتابة كل شيء لأن الـ bug صعب.

---

## مبدأ أساسي

> "أصلح بجراحة. لا تُعيد كتابة مكونات كاملة للتصليح." — من AGENTS.md

الـ bugs لها أسباب محددة. الجراحة الدقيقة دائماً أفضل من الاستئصال الكامل.

---

## البروتوكول — 5 خطوات إلزامية

### الخطوة 1: اقرأ الخطأ بالكامل

```
□ ما رسالة الخطأ الكاملة؟
□ أين يحدث؟ (file:line)
□ ما نوع الخطأ؟ (TypeError / NetworkError / LogicError / ...)
□ متى يحدث؟ (عند أي input / حالة / sequence من الأحداث)
```

**لا تبدأ بالتخمين قبل قراءة الخطأ كاملاً.**

### الخطوة 2: أعِد تمثيله ذهنياً

قبل فتح أي ملف:
```
اسأل نفسك: ماذا يجب أن يحدث؟ ماذا يحدث فعلاً؟
الفجوة بين الاثنين = مكان الـ bug
```

اكتب افتراضك: "أعتقد أن المشكلة في [X] بسبب [Y]"

### الخطوة 3: افحص الكود الفعلي

```
□ اقرأ السطر المذكور في stack trace
□ اقرأ 10 أسطر قبله وبعده
□ تتبّع كيف وصل البرنامج لهذه النقطة
□ تحقق من القيم المتوقعة عند كل خطوة
```

**لا تقرأ الملف كله** — ركز على الجزء المرتبط بالخطأ.

### الخطوة 4: عزّل السبب

```
□ هل المشكلة في هذه الدالة أم في ما يُمرَّر إليها؟
□ هل المشكلة في الـ state أم الـ logic؟
□ هل تحدث في كل الحالات أم حالة معينة؟
□ ما أصغر تعديل يمكن إثبات أنه يُحل المشكلة؟
```

**القاعدة:** ابحث عن السبب الجذري (root cause)، لا العرض (symptom).

### الخطوة 5: أصلح جراحياً

```
□ أصغر تغيير ممكن يحل المشكلة
□ لا تُعيد كتابة الدالة كلها إذا 3 أسطر تكفي
□ لا تُغيّر سلوك أجزاء أخرى لم تكن جزء من المشكلة
□ بعد الإصلاح: تحقق أن السبب الجذري اختفى
```

## قاعدة الـ 3 محاولات

إذا حاولت إصلاح نفس الـ bug 3 مرات وفشلت:

**توقف فوراً وافعل هذا:**

```
1. اذكر الافتراض الذي اعتمدت عليه في كل محاولة
2. حدد أيها كان خاطئاً (أو كل احتمال لماذا)
3. اسأل المستخدم سؤالاً واحداً محدداً:
   "جربت 3 أشياء وكلها فشلت. أعتقد أن المشكلة قد تكون في [X].
   هل [سؤال محدد عن X]؟"
```

**لا تُكمل بمحاولات عشوائية** بعد 3 فشل متتالي.

## أنماط الأخطاء الشائعة والحل السريع

### TypeError / AttributeError / KeyError
```
السبب المحتمل: بيانات null/undefined، تغيّر شكل الـ API
الفحص: تحقق من القيمة المتوقعة vs الفعلية بـ console.log أو print
الحل الجراحي: optional chaining، null check، أو default value
```

### CORS / Network Error
```
السبب المحتمل: URL خاطئ، headers ناقصة، أو مشكلة في server
الفحص: هل الـ request يصل للـ server؟ (check network tab)
الحل الجراحي: تحقق من URL، headers، وإعدادات CORS في الـ server
```

### Test Failures
```
السبب المحتمل: تغيّر الـ output، تغيّر الـ input المتوقع
الفحص: اقرأ failure message كاملاً (expected vs actual)
الحل الجراحي: أصلح الكود أو حدّث الـ test إذا السلوك الجديد مقصود
```

### Build Errors (TypeScript / Compilation)
```
السبب المحتمل: type mismatch، import خاطئ
الفحص: اقرأ أول error فقط — غالباً كل الأخطاء من نفس المصدر
الحل الجراحي: أصلح الـ root error أولاً قبل الأخرى
```

### Infinite Loop / Stack Overflow
```
السبب المحتمل: recursion بلا base case، event loop، circular dependency
الفحص: ابحث عن دالة تستدعي نفسها مباشرة أو عبر وسيط
الحل الجراحي: أضف base case أو كسر للـ loop
```

## ما لا تفعله أبداً

```
❌ إعادة كتابة component كاملة لأن bug واحد فيه
❌ تغيير interface عام لتجنّب bug في تنفيذ محدد
❌ إضافة try/catch لإخفاء الخطأ بدلاً من إصلاح السبب
❌ تعطيل اختبارات تفشل بدلاً من إصلاح الكود
❌ "cargo cult debugging" — تغيير عشوائي حتى يعمل
❌ Googling للـ error message مع أول نتيجة → تطبيقها عمياء
```

## Template للإبلاغ عن Bug

عند إبلاغ المستخدم عن bug أو طلب مساعدة:

```markdown
## 🐛 Bug Report

**الخطأ:**
```[error message كاملاً]```

**المكان:** [file:line]

**ما يجب أن يحدث:** [السلوك المتوقع]
**ما يحدث فعلاً:** [السلوك الفعلي]

**ما جربته:**
1. [المحاولة 1 + سببها]
2. [المحاولة 2 + سببها]

**افتراضي الحالي:** [السبب المحتمل]
**السؤال:** [سؤال واحد محدد]
```

## الفرق بين Debugging وإعادة الكتابة

| الموقف | الإجراء الصحيح |
|--------|---------------|
| Bug في سطر واحد | أصلح ذلك السطر فقط |
| Bug في منطق دالة واحدة | أصلح الدالة فقط |
| Design flaw يؤثر على وحدات متعددة | ناقش مع المستخدم قبل إعادة الكتابة |
| الكود "يعمل" لكن سيء | هذا refactoring، ليس bug fix |
| Bug في test | أصلح الـ test أو الكود، اشرح الفرق |
